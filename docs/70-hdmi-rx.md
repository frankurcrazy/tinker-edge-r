# HDMI capture with the Geekworm X1301 (TC358743)

## Hardware

The Geekworm X1301 (like the Auvidea B101) carries a Toshiba **TC358743XBG** HDMI-RX to
MIPI CSI-2 bridge with a 27 MHz reference crystal and a Raspberry-Pi-style 15-pin
2-lane CSI FPC; I2C address `0x0f`.  With two lanes it delivers up to 1080p30 or 720p60
4:2:2 (about 1 Gbit/s per lane).

The Tinker Edge R has two such 15-pin connectors:

| connector | MIPI RX | I2C | power switch | enable (CAM_GPIO) | ISP |
|---|---|---|---|---|---|
| CSI0 (ASUS default "OV5647") | `mipi_dphy_rx0` | I2C1 | GPIO0_B0 | GPIO2_A3 | ISP0 (`rkisp1_0`) |
| CSI1 (ASUS default "IMX219") | `mipi_dphy_tx1rx1` | I2C2 | GPIO2_B3 | GPIO2_A2 | ISP1 (`rkisp1_1`) |

## Kernel

* `media-hdmi-rx.config`: vendor `rkisp1` ISP driver (`VIDEO_ROCKCHIP_RKISP1`), MIPI
  D-PHY RX, and Rockchip's `tc35874x` driver (`VIDEO_TC35874X`, supports TC358743 and
  TC358749 and implements the `rkmodule` ioctls the vendor ISP uses).  The upstream
  `tc358743` driver claims the same compatible and stays off.
* Device tree: `hdmirx_csi0: tc358743@f` on I2C1 with `refclk` = 27 MHz fixed clock,
  2 data lanes, `link-frequencies = 297000000` (594 Mbit/s per lane, the Raspberry Pi
  overlay value) into `mipi_dphy_rx0` port 0, then `rkisp1_0`.  The default DTB enables
  it on **CSI0**; `rk3399pro-tinker-edge-r-hdmirx-csi1.dtb` (extlinux entry
  `hdmirx-csi1`) enables the CSI1 copy instead.  Without the board attached the bridge
  probe fails with an I2C error and the ISP simply has no source - harmless.

## Using it

```sh
hdmirx-setup                   # load EDID (1080p30 profile), query timings, configure the pipeline
hdmirx-setup status
hdmirx-setup capture 30        # 30 frames NV12 -> /tmp/hdmirx.nv12
```

`hdmirx-setup` does, in order:

1. `v4l2-ctl -d /dev/v4l-subdevN --set-edid=file=/usr/share/hdmirx/edid-1080p30.bin --fix-edid-checksums`
   - the source only sees modes advertised in the EDID.  Profiles generated by
   `src/rootfs/tools/mkedid.py`: `edid-1080p30.bin` (1080p30/25/24, 720p60/50, 480p/576p,
   LPCM audio) and `edid-720p60.bin`.  `v4l2-ctl --set-edid=type=hdmi` loads a generic
   1080p60 EDID, which a 2-lane link cannot carry.
2. `v4l2-ctl --query-dv-timings` / `--set-dv-bt-timings query` - lock to the incoming signal.
3. `media-ctl` - propagate `UYVY8_2X8/<w>x<h>` through `rkisp1-isp-subdev` pads 0 and 2
   (the vendor ISP passes YUV 4:2:2 through without Bayer processing).
4. `v4l2-ctl --set-fmt-video=...pixelformat=NV12` on the `rkisp1_mainpath` video node.

Then any V4L2 client works:

```sh
ffmpeg -f v4l2 -input_format nv12 -video_size 1920x1080 -framerate 30 -i /dev/video0 -c:v libx264 -preset ultrafast out.mp4
gst-launch-1.0 v4l2src device=/dev/video0 ! video/x-raw,format=NV12,width=1920,height=1080 ! videoconvert ! autovideosink
v4l2-ctl -d /dev/video0 --list-formats-ext
```

Audio: the TC358743 outputs HDMI audio on I2S pins; the X1301 does not route them to the
Tinker Edge R's connector, so audio is not captured (the EDID still advertises LPCM so
sources do not refuse the sink).

## Status and caveats

* Not tested on hardware.  Things to verify first: `dmesg | grep tc35874x` (chip id read,
  `+5V power present` when a cable is attached), `media-ctl -p` graph, whether the vendor
  ISP accepts the UYVY source format on `rkisp1-isp-subdev` pad 0 (if not, try
  `YUYV8_2X8`, or switch `CONFIG_VIDEO_TC35874X`/`CONFIG_VIDEO_TC358743` and the
  `isp0`/`rkisp1_0` nodes to the upstream pairing).
* If the bridge is on CSI1, boot the `hdmirx-csi1` extlinux entry.
* Raspberry Pi cameras (OV5647 v1.3, IMX219 v2) can be described on the same connectors
  with the upstream bindings; the drivers are built as modules (`ov5647`, `imx219`).
